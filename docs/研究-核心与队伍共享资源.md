# Mindustry 核心建筑与队伍共享资源研究（移植参考）

> 目标：为方块工业（NeoForge 1.21.1）移植提供「核心建筑 + 队伍共享资源」的设计依据喵。
> 源码根：`D:\Blockdustry\Mindustry\core\src\mindustry\` 喵。

## 1. 概览

- 核心（Core）是 Mindustry 里每个队伍最重要的建筑：物品总仓库、玩家/单位重生点、采集物流终点、攻击模式胜利判定标的喵。
- 类：`CoreBlock extends StorageBlock`（`world/blocks/storage/CoreBlock.java`），实体内部类 `CoreBuild extends Building` 喵。
- 核心建筑本身不主动生产、不主动卸货，只负责**接受**物品，是物流网络的目的地喵。
- **队伍共享资源 = 同队所有核心指向同一个 `ItemModule` 实例**，本质是「以核心实体为锚的、跨核心共享的可变物品容器」喵。

- `armor`：物理减伤（bastion 5、citadel 10、acropolis 15），普通核心无护甲喵。

## 3. CoreBuild 的物品存储方式

### 3.1 数据载体：`Building.items`（`ItemModule`）

- 每个建筑实体有字段 `@Nullable ItemModule items`（BuildingComp.java 行 83）喵。
- `ItemModule`（`world/modules/ItemModule.java`）是「按物品 ID 的 int 数组 + 总数 total + 轮询指针 takeRotation」的紧凑容器，提供 `get/set/add/remove/has/take/clear` 等 API 喵。
- 注意 `ItemModule` 的 `get` 按 `item.id` 索引数组，`add`/`remove` 维护 `total`，`take()` 做轮询取货喵。
- 容量：`getMaximumAccepted(item)` 默认返回 `block.itemCapacity`，CoreBuild 覆写成 `coreIncinerates ? Integer.MAX_VALUE/2 : storageCapacity`，即**每种物品单独按 `storageCapacity` 封顶**（不是所有物品共用总容量）喵。
- 核心存储条 UI：`items.total() / (storageCapacity * 已解锁物品数)`，暗示理论总容量 = `storageCapacity × 物品种类数` 喵。

### 3.2 接受与取出（物流接口）

- `CoreBuild.acceptItem(source, item)`：`coreIncinerates || items.get(item) < getMaximumAccepted(item)`，即满则拒（除非规则允许焚毁）喵。
- `handleItem(source, item)`：满了就触发焚毁特效并把物品销毁（`incinerateEffect`），否则 `super.handleItem` 直接 `items.add(item, 1)` 喵。
- `handleStack`/`removeStack`：按数量批量入/出；移除时同步 `sector.info`（战役统计）喵。
- 单位补货：单位靠近核心时，由单位侧 `UnitComp` 的补货逻辑从核心 `items` 取（核心实现 `allowResupply` 语义），核心本身不主动卸货喵。
- `canUnload()`：受 `block.unloadable && state.rules.allowCoreUnloaders` 控制（默认规则下卸载器可从核心取货）喵。

### 3.3 每队核心数量与归属

- 一队可以有**多个核心**：`TeamData.cores` 是 `Seq<CoreBuild>`（无长度限制），`Team.core()` 只是取 `cores.first()`（见 `game/Teams.java` 行 464）喵。
- 归属队伍：核心与所有建筑一样有 `team` 字段；放置瞬间确定队伍（`tile.setBlock(this, team)`），`placed()` 时调用 `state.teams.registerCore(this)` 注册进 `TeamData.cores` 喵。
- 销毁时 `onDestroyed`/`onRemoved` 调用 `unregisterCore`，当 `cores` 清空则 `TeamData.active()` 变 false（队伍从活跃列表移除），这是**游戏胜利/消灭判定**的核心依据（攻击模式 `isAlive() == hasCore()`）喵。
- 放置限制：`canPlaceOn` 要求已有同队核心（非编辑器）且地板 `allowCorePlacement` 或站在旧核心上；即普通模式下第二个核心必须是升级放置，多核心主要出现在编辑器/沙盒喵。

## 4. 队伍共享资源机制（重点）

### 4.1 Mindustry 没有独立的「队伍级资源池」类

- `Team` 类（`game/Team.java`）**没有** `storage`/`items` 字段、也没有 `Team.storage()` API 喵。
- 但 `Team.items()` 存在，签名与实现（行 83-85）：

```java
public ItemModule items(){
    return core() == null ? ItemModule.empty : core().items;
}
```

- `Team.core()` 返回 `data().core()`（第一颗核心）；`Team.cores()` 返回 `state.teams.cores(this)` 喵。
- 因此「队伍共享资源池」的**语义实现**是：同队所有核心共享同一个 `ItemModule` 实例，`Team.items()` 只是拿到第一颗核心的那个共享实例喵。

### 4.2 核心如何「合并」为一份存储：`onProximityUpdate`

这是整个机制的心脏（CoreBlock.java 行 704-735）喵：

```java
public void onProximityUpdate(){
    super.onProximityUpdate();
    // 1. 把本核心的 items 指向同队其它核心的同一实例（首次放置时没有其它核心则新建）喵
    for(Building other : state.teams.cores(team)){
        if(other.tile != tile){
            this.items = other.items;
        }
    }
    state.teams.registerCore(this);

    // 2. 计算本核心的存储容量 = 自身 itemCapacity + 紧邻的 coreMerge 存储块容量喵
    storageCapacity = itemCapacity + proximity.sum(e -> owns(e) ? e.block.itemCapacity : 0);
    // 3. 让紧邻的 container/vault 也指向同一 items 实例，并记录 linkedCore 喵
    proximity.each(this::owns, t -> {
        t.items = items;
        ((StorageBuild)t).linkedCore = this;
    });

    // 4. 把所有核心的容量求和（自身 + 其它核心及其紧邻存储），并广播给所有核心喵
    for(Building other : state.teams.cores(team)){
        if(other.tile == tile) continue;
        storageCapacity += other.block.itemCapacity + other.proximity.sum(e -> owns(other, e) ? e.block.itemCapacity : 0);
    }
    ...
    for(CoreBuild other : state.teams.cores(team)){
        other.storageCapacity = storageCapacity;
    }
}
```

要点：

- **跨核心共享**：同队所有核心的 `items` 指向**同一个 `ItemModule` 对象**，所以任何核心入货=全队入货，任何核心取货=全队取货喵。
- **容量合并**：`storageCapacity` 是全队求和（所有核心 itemCapacity + 紧邻可合并存储块容量），每个核心/存储块都用同一个总容量判断满否喵。
- **就近并入存储块**：`StorageBlock`（container/vault）默认 `coreMerge = true`，紧邻核心时 `items` 被改指向核心的 items，`linkedCore` 记录核心，`acceptItem`/`handleItem`/`removeStack` 全部转发给核心（StorageBlock.java 行 50-141）喵。`reinforcedContainer` 等 `coreMerge = false` 的块不并入喵。
- **不并入时的独立性**：没有核心的存储块各自持有自己的 `ItemModule`，`separateItemCapacity = true` 喵。
- **核心被拆时归还**：`onRemoved`（行 803-820）按容量比例把共享物品分摊回原存储块自己的新 `ItemModule`，并把 `linkedCore` 清空喵。

### 4.3 全队物品是共享取用还是每核心独立

- **共享取用**喵。所有同队核心（及其并入的容器）读写的都是同一份 `ItemModule`，没有每核心独立库存喵。
- 唯一差异在**容量**：虽然实例共享，但每个核心都各自持有 `storageCapacity`（且最终都等于全队求和值），所以满载判定在全队层面一致喵。

### 4.4 相关 API 清单

| API | 位置 | 作用 |
|-----|------|------|
| `Team.items()` | Team.java | 返回第一颗核心的共享 ItemModule（无核心返回空常量） |
| `Team.core()` / `Team.cores()` | Team.java | 第一颗核心 / 全部核心 |
| `Team.data()` | Team.java | 返回 `TeamData`（含 cores、unitCap、unitCount、buildingTypes 等） |
| `Teams.registerCore/unregisterCore` | Teams.java | 核心加入/移出 `TeamData.cores` 并维护 active 列表 |
| `Teams.get(team).cores` | Teams.java | 队伍核心列表（勿修改） |
| `CoreBuild.onProximityUpdate` | CoreBlock.java | 合并 items 实例与容量（共享机制核心） |
| `StorageBuild.linkedCore` | StorageBlock.java | 存储块→核心的归属指针 |

## 5. 单位重生与核心

- 核心**兼作队伍重生点**喵。`CoreBlock.allowSpawn` 控制是否允许重生（默认 true）喵。
- 流程：玩家死亡 → `PlayerComp.update` 中 `deathTimer` 到点 → `core.requestSpawn(self())`（PlayerComp.java 行 233-242）→ `requestSpawn` 校验环境支持与 `allowSpawn` → `Call.playerSpawn(tile, player)`（CoreBlock.java 行 585-590）喵。
- `playerSpawn`（RPC，服务器执行）：在核心处生成 `unitType` 单位，`player.set(core)` 归位、`unit.controller(player)` 接管，重置武器装填防瞬射喵。
- `bestCore()`（PlayerComp.java 行 121-126）：选「最大且最近」的核心，按 `size` 倒序优先，再按距离升序；只选环境支持的单位喵。
- 手动重生：玩家死亡后点击核心，`onControlSelect` → `requestSpawn` 喵。
- 单位上限：核心通过 `unitCapModifier` 贡献队伍单位上限；`BlockIndexer` 在建放置/拆除时对 `TeamData.unitCap` 累加/扣除，`Units.getCap` = 规则基础上限（`state.rules.unitCap`，可选加 `data().unitCap`）喵。波次队、关闭单位上限时返回无穷喵。

## 6. 方块工业迁移建议（重点）

### 6.1 现状梳理（Blockdustry）

- `BlockdustryBuildingEntity`：单品种本地库存 `storedItem/storedCount/itemCapacity`，实现 `BlockdustryItemSink/Source`，多格建筑用 `anchor` 锚点 + `CORNER` 方块状态喵。
- `BlockdustryTeam`/`BlockdustryTeams`：队伍用 ServerLevel 的 `BLOCK_TEAM` attachment（`Map<BlockPos, Team>`）与实体 `ENTITY_TEAM` attachment 保存喵。
- 物流：`BlockdustryItemSink.acceptItem/handleItem` + `BlockdustryItemSource.getTeam/getPos`，传送带/Router 走这套接口喵。
- 方块注册：`BlockdustryBuildingBlock`（size、CORNER、EntityBlock）+ `BlockdustryBuildingItem` 喵。

### 6.2 迁移总体结论

- Mindustry 的「队伍共享资源」本质上绑定在核心实体上，但为了 MC 的存续与多核心一致性，**推荐用 Level attachment 做队伍级共享存储**，核心实体只是该存储的读写入口喵。
- 容量语义沿用「每种物品单独封顶 = 全队核心容量之和」，不做全局无限（除非将来做 `coreIncinerates` 焚毁规则）喵。
- 核心仍是多格建筑（size 3~5），沿用现有 `anchor` + `CORNER` 多格方案，仅锚点格参与逻辑喵。

### 6.3 队伍共享存储设计（推荐）

新增类 `TeamItemStorage`（可放 `team` 包）：

```java
// 队伍共享物品存储：忠于 Mindustry ItemModule 的「按物品种类 + per-item 容量」语义喵
public class TeamItemStorage {
    private final Object2IntMap<Item> items = new Object2IntOpenHashMap<>(); // 物品 -> 数量喵
    private int itemCapacity; // 单物品种类容量（Mindustry storageCapacity，全队求和）喵

    public int get(Item item) { return items.getInt(item); }
    public boolean accepts(Item item) { return get(item) < itemCapacity; }
    public boolean add(Item item, int amount) {  // 返回实际放入数喵
        int space = itemCapacity - get(item);
        int put = Math.min(amount, Math.max(space, 0));
        items.addTo(item, put);
        return put;
    }
    public int take(Item item, int amount) {     // 返回实际取出数喵
        int t = Math.min(amount, get(item));
        items.addTo(item, -t);
        if (get(item) == 0) items.removeInt(item);
        return t;
    }
    public int total() { /* 遍历求和 */ }
    public void setCapacity(int capacity) { this.itemCapacity = capacity; }
    public void write(CompoundTag tag, HolderLookup.Provider p);
    public void read(CompoundTag tag, HolderLookup.Provider p);
}
```

在 `BlockdustryAttachments` 注册 Level 级 attachment：

```java
// 队伍共享物品池：Map<BlockdustryTeam, TeamItemStorage> 挂 ServerLevel，持久化喵
public static final DeferredHolder<AttachmentType<?>, AttachmentType<Map<BlockdustryTeam, TeamItemStorage>>> TEAM_ITEMS =
    ATTACHMENT_TYPES.register("team_items",
        () -> AttachmentType.<Map<BlockdustryTeam, TeamItemStorage>>builder(() -> new HashMap<>())
            .serialize(getTeamItemsSerializer())
            .build());
```

静态门面 `BlockdustryTeamStorage`（提供与现有 `BlockdustryTeams` 一致的静态调用风格）：

```java
public final class BlockdustryTeamStorage {
    public static TeamItemStorage get(ServerLevel level, BlockdustryTeam team);       // 无则返回空常量喵
    public static TeamItemStorage getOrCreate(ServerLevel level, BlockdustryTeam team);
    public static void remove(ServerLevel level, BlockdustryTeam team);               // 队伍无核心时清理喵
    public static int get(ServerLevel level, BlockdustryTeam team, Item item);
    public static int take(ServerLevel level, BlockdustryTeam team, Item item, int amount);
    public static boolean accepts(ServerLevel level, BlockdustryTeam team, Item item);
}
```

选型理由：

- **为什么用 Level attachment 而不是核心实体字段**：多核心共享需要「跨方块实体共享同一可变对象」，MC 的 BE 字段无法保证多 BE 共享同一实例且生命周期可控；挂 Level 则天然共享、天然随档持久化喵。
- **与现有 `BLOCK_TEAM` attachment 模式一致**：都是 `DeferredHolder<AttachmentType<?>, ...>` + 自定义 serializer，工程风格统一喵。
- **生命周期**：核心 `placed()` 时 `getOrCreate` 并累加容量；核心拆除时重新遍历同队剩余核心算容量，无核心则 `remove` 清理队伍存储喵（对应 Mindustry 的「无核心=队伍被消灭」）。

### 6.4 核心方块/实体设计

```java
// 核心方块：多格、大容量、不可被破坏（可选）、不主动卸货喵
public class BlockdustryCoreBlock extends BlockdustryBuildingBlock {
    private final int itemCapacity;   // 单核心基础容量（4000/9000/13000...）喵
    private final boolean allowSpawn; // 是否允许重生喵
    public BlockdustryCoreBlock(Properties props, Supplier<BlockEntityType<?>> entityType,
                                int size, int itemCapacity, boolean allowSpawn) {
        super(props, entityType, size);
        this.itemCapacity = itemCapacity;
        this.allowSpawn = allowSpawn;
    }
}

// 核心实体：不占本地 storedItem，全部委托给队伍共享存储喵
public class BlockdustryCoreBlockEntity extends BlockdustryBuildingEntity {
    // 队伍共享存储访问喵
    public TeamItemStorage storage() {
        return BlockdustryTeamStorage.getOrCreate((ServerLevel) level, getTeam());
    }

    // 核心作为物流终点：预检 = 同队 + 队伍存储可收喵
    @Override public boolean acceptItem(BlockdustryItemSource source, Item item) {
        if (source == null || item == null) return false;
        if (!getTeam().canInteract(source.getTeam())) return false;
        return storage().accepts(item);
    }

    // 移交：直接入队伍存储喵
    @Override public boolean handleItem(BlockdustryItemSource source, Item item) {
        if (!acceptItem(source, item)) return false;
        storage().add(item, 1);
        setChanged();
        return true;
    }

    // 容量 = 全队求和（Mindustry storageCapacity），由注册/拆除时维护喵
    @Override public int getCapacity() {
        return BlockdustryTeamStorage.getCapacity((ServerLevel) level, getTeam());
    }
}
```

要点：

- 核心**不覆写 `storeItem/removeOne` 本地库存路径**，而是直接实现接口方法走队伍存储，避免与基类单品种库存冲突；建议给 `BlockdustryBuildingEntity` 增加 `protected boolean usesTeamStorage()` 之类的开关，或让核心 override 掉所有本地库存方法喵。
- 多格：沿用 `BlockdustryBuildingBlock` 的 size + `CORNER` + `anchor`，仅锚点格 BE 参与 tick；非锚点格只是占位方块喵。
- 容量维护：新增/升级核心时把该核心 `itemCapacity` 加进队伍容量；拆除时从队伍容量中减掉并重新对同队剩余核心求和；容量也可考虑并入紧邻的 container/vault（如果后续实现 `coreMerge` 存储块）喵。
- 可选增强：`coreIncinerates` 对应「物品溢出焚毁」规则；`incinerateNonBuildable` 对应「不可建造物品直接焚毁」（配合石墨等自定义物品时有用）喵。

### 6.5 与现有物流的对接

- 现有 `BlockdustryItemSink/Source` 接口**无需改动**：核心实体实现 `BlockdustryItemSink`，传送带/Router 的 `dumpItem` 会对核心 `acceptItem/handleItem`，自然汇入队伍存储喵。
- 需要新增/调整的是「取货侧」：Mindustry 用 `Unloader`（卸载器）从核心按物品类型取货。若移植卸载器，让它实现 `BlockdustryItemSource`，取货时调 `BlockdustryTeamStorage.take(level, team, item, 1)` 喵。
- 单位补货（Resupply）：单位实体可仿照 `BlockdustryTeamStorage.take` 从队伍存储补弹药/物品，核心本身不卸货喵。
- 注意队伍判定：`acceptItem` 里必须保留 `getTeam().canInteract(source.getTeam())`，否则敌方传送带可往核心塞货喵。

### 6.6 容量与无限策略

- 推荐默认：**每种物品封顶 = 队伍容量总和**（忠于 Mindustry），不设全局无限喵。
- 数值建议沿用原作：shard 4000 / foundation 9000 / nucleus 13000 / bastion 2000 / citadel 3000 / acropolis 4000；size 3/4/5/4/5/6 喵。
- 后续可加规则项 `coreIncinerates`：满时溢出焚毁（Mindustry 战役默认），需要时在 `handleItem` 中实现焚毁特效与计数喵。
- 持久化：`TeamItemStorage` 走 attachment serializer 随档保存；若担心大存档体积，可改为只存非零物品条目（现有 `BLOCK_TEAM` serializer 已是按需写入）喵。

### 6.7 明确落地步骤（建议顺序）

1. 新增 `TeamItemStorage` + `BlockdustryTeamStorage` 门面 + `TEAM_ITEMS` attachment 喵。
2. 新增 `BlockdustryCoreBlock`（多格）+ `BlockdustryCoreBlockEntity`（委托队伍存储）喵。
3. 在 `BlockdustryBlocks` 注册 core-shard（或先只做一个演示核心），加入创造栏喵。
4. 处理队伍容量生命周期：`placed()`/拆除时维护 `TeamItemStorage.capacity` 喵。
5. 可选：实现重生（`allowSpawn` 重生点 + 死亡重生队列）、卸载器取货、`coreMerge` 存储块并入喵。
