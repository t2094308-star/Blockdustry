# 研究：双管炮炮弹飞行卡顿喵

> 结论（一句话）：炮弹只在服务端 `move()`，客户端不同步模拟移动，位置只能靠服务端位置包每 3 tick 才发一次的阶梯跳变更新，而渲染插值 `lerp(xOld, getX(), partialTick)` 因为客户端 `xOld == getX()` 完全失效 → 炮弹以 ~6.7Hz、每次跳 ~2.4 格的方式"瞬移"飞行，肉眼就是"奇怪卡顿"喵。

## 一、三个文件分析喵

### 1. `src/main/java/com/blockdustry/entities/BlockdustryBulletEntity.java`（根因所在）喵

- `tick()` 第 60 行：`super.tick()` 之后立刻 `if (this.level().isClientSide) return;`，**客户端根本不调用 `move()`**，只有服务端第 66 行才 `move(MoverType.SELF, deltaMovement)` 喵。
- 客户端炮弹实体的 x/y/z 只会在收到服务端位置包时改变（`lerpTo` → `setPos` 瞬移）喵。
- 第 40 行 `noPhysics = true` 只写在业务构造器里；客户端是用 2 参构造器 `(EntityType, Level)` 从 add-entity 包重建的，客户端 `noPhysics` 是 `false`（不影响当前卡顿，但影响修复：客户端若直接 `move()` 会撞方块喵）。
- `life`、`ownerTeam`、`damage` 都没进 `defineSynchedData`，不同步喵。
- 没有调用原版 `shoot()`，因此 `hasImpulse=false`、`yaw/pitch` 从未设置（不影响渲染，渲染器用 velocity 不用 rotation）喵。

### 2. `src/main/java/com/blockdustry/building/TurretBlockEntity.java`（发射逻辑正常）喵

- 发射、预判、装填都正常；`BULLET_SPEED=0.8` 格/tick（很快），方向含小随机散布喵。
- 不开火不影响卡顿，卡顿是实体同步/渲染层面的喵。

### 3. `src/main/java/com/blockdustry/client/BlockdustryBulletRenderer.java`（渲染器本身没毛病）喵

- `EntityRenderDispatcher`/`LevelRenderer` 早已在渲染前按 `lerp(xOld, getX(), partialTick)` 平移好 pose，渲染器无需自己平移喵。
- quad 方向取 `entity.getDeltaMovement()`：客户端出生包（`ClientboundAddEntityPacket`）带初始速度、`trackDeltas()` 默认 true 使 spawn 时还会补发一个 `ClientboundSetEntityMotionPacket`，之后服务端速度恒定不再发 → 客户端速度恒定 → **quad 朝向恒定，不会突变**，排除"朝向突变"导致卡顿喵。
- 真正的问题：`xOld` 与 `getX()` 恒等，插值结果是常数，方向/大小都平滑不了喵。

## 二、原版投射物机制对照（1.21.1 源码确认）喵

### 雪球（`ThrowableProjectile.tick()`，`ThrowableItemProjectile` 之父类）喵

```java
public void tick() {
    super.tick();                       // Projectile.tick → Entity.baseTick
    ...命中检测...
    Vec3 vec3 = this.getDeltaMovement();
    this.setDeltaMovement(vec3.scale(f)); // 阻力
    this.applyGravity();                  // 重力
    this.setPos(d0, d1, d2);              // 双端都移动！
}
```

**没有任何 `isClientSide` 分支，客户端也逐 tick 用 velocity 更新位置**喵。

### 箭（`AbstractArrow.tick()` 第 300 行）喵

```java
this.setPos(d7, d2, d3);   // 双端都移动！
```

同样客户端也模拟飞行喵。

### 客户端渲染插值链路（为什么原版平滑）喵

- `ClientLevel.tickNonPassenger()` 每次 tick 实体前先调 `entity.setOldPosAndRot()`，把 `xOld/yOld/zOld` 记为"本 tick 开始时的位置"喵。
- `LevelRenderer.renderEntity()` 用 `Mth.lerp(partialTick, entity.xOld, entity.getX())` 画 → 只要实体本 tick 位置有变化（客户端自模拟），渲染帧率下就平滑喵。
- 客户端自模拟 + 服务端位置包只做校正 → 原版投射物看起来丝滑喵。

### 服务端同步（为什么我们更卡）喵

- `ServerEntity.sendChanges()`：`if (this.tickCount % this.updateInterval == 0 || hasImpulse || entityData.isDirty())` 才发位置包喵。
- `EntityType.Builder` 默认 `updateInterval = 3`，我们的注册 `BlockdustryEntities.java` **没设 `.updateInterval(...)`** → 位置包每 3 tick 才发一次 ≈ **6.7Hz**喵。
- 我们没调 `shoot()`（`hasImpulse=false`）、`defineSynchedData` 为空（`entityData.isDirty()=false`）→ 没有额外触发，坐实 3 tick 一发喵。
- 客户端 `Entity.lerpTo()` 就是 `setPos(x,y,z)` **直接瞬移**，1.21.1 没有任何 lerpSteps 平滑喵。
- 对照：原版箭 `.updateInterval(20)`、雪球 `.updateInterval(10)`，它们敢这么低频是因为客户端自己模拟了喵。

## 三、卡顿链路（根因推导）喵

1. 服务端每 tick `move()` 0.8 格喵。
2. 但位置同步包每 3 tick 才发一次（updateInterval=3）→ 包与包之间客户端位置不动喵。
3. 客户端收到包 `lerpTo` 直接 `setPos` 瞬移；又因客户端自己不移，`setOldPosAndRot()` 之后 `xOld == getX()` → `lerp(xOld, getX(), partialTick)` 恒等于当前值 → **插值失效**喵。
4. 结果：炮弹以 ~6.7Hz、每跳 ~2.4 格（3×0.8）的阶梯状飞行，高帧率下看得一清二楚喵。
5. 即便把 `updateInterval` 改成 1（20Hz），不做客户端自模拟的话仍是每 3 帧跳一次，60/144fps 下依旧可见卡顿 → **必须客户端自模拟**喵。

## 四、解决方案与原因喵

### 方案一（推荐，最小改动）：客户端也 `move()`，对齐原版投射物喵

改 `BlockdustryBulletEntity.java` 喵。

```java
// 2 参构造器：客户端重建时也走这里，必须保证客户端也 noPhysics，避免客户端 move 撞方块与服务端产生分歧喵
public BlockdustryBulletEntity(EntityType<BlockdustryBulletEntity> type, Level level) {
    super(type, level);
    this.noPhysics = true;
}

@Override
public void tick() {
    super.tick();   // 保持 baseTick 在最前（流体/传送门/着火等前置处理，原版投射物也是先 super.tick 再移动）喵
    // 双端都移动：客户端自模拟后 xOld!=getX()，LevelRenderer 的 partialTick 插值立即恢复平滑喵
    this.move(MoverType.SELF, this.getDeltaMovement());
    if (this.level().isClientSide) {
        return;     // 客户端不处理寿命/命中，等服务端 discard 的移除包即可喵
    }
    if (--life <= 0) {
        this.discard();
        return;
    }
    ...（原有命中活体/建筑逻辑不变）...
}
```

原因：客户端逐 tick `move()` 后，`ClientLevel.tickNonPassenger` 的 `setOldPosAndRot()` 让 `xOld` 保持上一 tick 位置，`LevelRenderer.renderEntity` 的 `lerp` 在渲染帧率下平滑补间；服务端位置包只做微小校正，双端速度一致所以不会互相打架喵。

副作用与对策喵：
- 客户端会比服务端多飞约 1 个 RTT（约 0.8 格）才被移除包清掉 → 可接受；若要精确对齐，见"方案四"喵。
- 命中逻辑只留服务端（保持现状）喵。

### 方案二（辅助）：注册时把 `updateInterval` 设为 1 喵

改 `BlockdustryEntities.java` 喵。

```java
ENTITY_TYPES.register("bullet",
        () -> EntityType.Builder.<BlockdustryBulletEntity>of(BlockdustryBulletEntity::new, MobCategory.MISC)
                .sized(0.25f, 0.25f)
                .updateInterval(1)   // 位置包每 tick 一发，减小校正步长喵
                .build("bullet"));
```

原因：降低服务端位置包间隔，客户端校正更密、更准（治标）；真正治本仍是方案一的客户端自模拟喵。

### 方案三（重构，可选）：直接继承 `ThrowableProjectile` 喵

让基类自带双端 tick 移动 + `updateRotation()` 朝向更新，省去手写 `move()` 喵。注意点喵：
- 基类有重力/阻力/方块命中逻辑，需要在 tick 里重写或 `noPhysics` 化才能保持"子弹穿透"设定喵；
- 命中活体/建筑逻辑仍需自定义，且基类命中回调 `onHitEntity/onHitBlock` 需要接管喵。

### 方案四（可选优化）：同步 `life`，让客户端到点停止，避免超飞喵

把 `life` 放 `SynchedEntityData`（`builder.define(DATA_LIFE, 0)`，`setLife` 时 `entityData.set`），`onSyncedDataUpdated` 回填本地字段；客户端 `life<=0` 时停止移动但不 discard，等服务端移除包喵。这样客户端子弹终点与服务端完全一致喵。

### 关于渲染器 quad 的补充说明喵

- **不需要改 pose 平移**：插值平移由 `EntityRenderDispatcher`/`LevelRenderer` 完成，渲染器只管画喵。
- **不需要平滑 quad 朝向**：速度恒定、朝向稳定；若将来加抛物线/转向，再用 `entity.getViewYRot(partialTick)`（yaw 插值）驱动 quad 即可喵。
- **关于 `super.tick()` 与 `move()` 顺序**：保持 `super.tick()` 在前（原版 `ThrowableProjectile`/`AbstractArrow` 均如此），`move()` 在后即可喵。
