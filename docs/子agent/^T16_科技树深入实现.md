# T16 科技树（Tech Tree）深入实现喵

## 目标喵
在 T14（Mindustry 机制研究）基础上，深挖 Blockdustry（MC/NeoForge 1.21.1）科技树的**可落地实现**：数据层、存档、门控、UI、成本与默认解锁，输出类/文件清单与并行拆分喵。

## 零、总体决策（速览）喵
| 决策点 | 结论 | 理由喵 |
|---|---|---|
| 节点定义 | v1 Java 静态注册；v2 可选 JSON 数据包（DataPackRegistry） | 贴合现有 DeferredRegister 风格、双端天然一致、编译期安全喵 |
| 存档 | `ResearchSavedData extends SavedData` 挂 `server.overworld()` | 显式 setDirty、按世界隔离、跨维度共享；比 Level attachment 规避 dirty 标记坑喵 |
| 同步 | 加入服务器全量推送 `ResearchStatePayload`；变更增量广播 | 沿用现有 payload 模式，客户端无需查询即可开屏喵 |
| 门控 | 服务端 `BlockEvent.EntityPlaceEvent` 取消放置 + 提示 | 不侵入 `BlockdustryBuildingItem`（共享文件），新文件独立订阅喵 |
| UI | `ResearchScreen` 竖排缩进树（v1）+ 进度条 + 按键 J | 先列表后连线树，最稳落地喵 |
| 材料来源 | v1 玩家背包；v2 队伍共享池优先 | 背包独立无队伍绑定；共享池已有 `BlockdustryTeamStorage` 可复用喵 |
| 默认解锁 | core / conveyor / router / drill / power_node / combustion_generator | 对应 Mindustry 开局免费节点喵 |

## 一、数据层喵

### 1.1 注册方式对比与选择喵
| 方式 | 优点 | 缺点 | 结论喵 |
|---|---|---|---|
| Java 静态注册（`ResearchNodes.java`） | 编译期安全、双端一致、无同步/编解码、贴合现有 mod 风格 | 改树需改代码；modpack 不能扩展 | **v1 主选**，Mindustry 原版 Serpulo/Erekir 树就是 Java 嵌套 builder，非 JSON 喵 |
| JSON 数据包（`DataPackRegistry`，`data/blockdustry/research_node/*.json`） | 数据驱动、可 /reload、modpack 可加节点 | 需注册 Registry Key + CODEC + 网络 CODEC + 同步时序；错误运行时才暴露 | v2 增强，格式见 1.3，迁移路径清晰喵 |
| `SimpleJsonCodec`（Fabric 系/手写 loader） | 无需注册表 | NeoForge 1.21.1 无官方对应，需自写 Gson loader 与同步，重复造轮子 | 不推荐喵 |

**结论**：v1 用静态注册，理由是本 mod 全部内容（方块/物品/实体）都是 `DeferredRegister` 静态注册，无任何数据包 registry；树结构双端必须完全一致，静态注册天然满足，免去 datapack 同步与编解码复杂度喵。同时 1.3 给出完整 JSON schema，若后续要 modpack 扩展，按 1.2 的 CODEC 转数据包即可，节点内存模型不变喵。

### 1.2 ResearchNode 字段与 CODEC 喵
`com.blockdustry.research.ResearchNode`（record + builder）喵：
```java
public record ResearchNode(
        ResourceLocation id,                      // 节点 id（blockdustry:drill）喵
        List<ResourceLocation> parents,           // 前置节点数组，支持多父（多父同时解锁才可研究）喵
        ResourceLocation unlockContent,           // 解锁内容（方块/物品 RL），gate 与创意栏过滤用喵
        boolean defaultUnlocked,                  // 默认解锁（根/基础节点）喵
        Map<ResourceLocation, Integer> requirements,   // 显式研究材料需求 item->count（v1 主路径）喵
        Map<ResourceLocation, Integer> buildCost,      // v2 公式用：建造配方基础物量喵
        float costMultiplier,                     // 累计成本倍率，子继承父（Mindustry researchCostMultiplier）喵
        Map<ResourceLocation, Float> perItemMultiplier // 按物品追加倍率，子继承父喵
) {
    public static Builder builder(String path) { ... } // 便捷建 blockdustry:path 喵
}
```
关键点：`requirements` 存**显式需求**，v1 直接用它，不跑公式；`costMultiplier`/`perItemMultiplier` 在加载期由 `ResearchTree` 从父链继承并按祖先累乘，得到每节点的**有效需求**喵。

### 1.3 JSON 数据格式（v2，DataPackRegistry 用）喵
`data/blockdustry/research_node/drill.json`：
```json
{
  "id": "blockdustry:drill",
  "parents": ["blockdustry:core"],
  "unlock": "blockdustry:drill",
  "defaultUnlocked": false,
  "requirements": [ { "item": "minecraft:coal", "count": 30 } ],
  "buildCost": { "minecraft:cobblestone": 6, "minecraft:oak_log": 2 },
  "costMultiplier": 1.0,
  "perItemMultiplier": { "minecraft:coal": 1.0 },
  "objectives": []
}
```
CODEC（`ResearchNode.CODEC`，MapCodec + 网络 StreamCodec）喵：
```java
public static final MapCodec<ResearchNode> CODEC = RecordCodecBuilder.mapCodec(i -> i.group(
    ResourceLocation.CODEC.fieldOf("id").forGetter(ResearchNode::id),
    ResourceLocation.CODEC.listOf().optionalFieldOf("parents", List.of()).forGetter(ResearchNode::parents),
    ResourceLocation.CODEC.fieldOf("unlock").forGetter(ResearchNode::unlockContent),
    Codec.BOOL.optionalFieldOf("defaultUnlocked", false).forGetter(ResearchNode::defaultUnlocked),
    Codec.mapPair(ResourceLocation.CODEC.fieldOf("item"), Codec.INT.fieldOf("count")).codec()
        .listOf().optionalFieldOf("requirements", List.of())
        .xmap(l -> l.stream().collect(Collectors.toMap(Pair::getFirst, Pair::getSecond)),
              m -> m.entrySet().stream().map(e -> Pair.of(e.getKey(), e.getValue())).toList())
        .forGetter(ResearchNode::requirements),
    // buildCost / costMultiplier / perItemMultiplier 同上省略喵
).apply(i, ResearchNode::new));
```
注册（`ResearchDataPackRegistry`，v2 单独文件，`@EventBusSubscriber(modid, bus=MOD)`）喵：
```java
@SubscribeEvent
static void register(RegisterDataPackRegistriesEvent event) {
    event.dataPackRegistry(ResearchTree.REGISTRY_KEY, ResearchNode.CODEC.codec(), ResearchNode.STREAM_CODEC);
}
```

### 1.4 ResearchTree：依赖图构建喵
`com.blockdustry.research.ResearchTree`（静态单例，惰性初始化）喵：
- `Map<ResourceLocation, ResearchNode> byId`：节点查找喵。
- `Map<ResourceLocation, List<ResourceLocation>> children`：父->子反向索引，遍历与画树用喵。
- `Map<ResourceLocation, Integer> depth`：父.depth+1，根=0，画树缩进用喵。
- `List<ResearchNode> roots`：无父的节点（如 core）喵。
- `Map<ResourceLocation, ResearchNode> byUnlock(Block/Item RL)`：门控查「内容->节点」用喵。
- `Map<ResourceLocation, Map<RL,Integer>> effectiveRequirements(id)`：沿父链继承倍率累乘后返回每节点有效需求（懒计算缓存）喵。
- 惰性初始化：静态 `get()` 用双检锁建一次（线程安全、可在任意线程首次触发，无需改 `Blockdustry.java`）喵。
- 校验：重复 id、父不存在、requirements 里 item 不存在、unlock 内容解析失败 → 启动日志告警并跳过，不崩溃喵。

### 1.5 成本计算喵
`com.blockdustry.research.ResearchCost` 喵：
```java
public static int researchCost(float mult, int buildAmount, float perItemMult) {
    // Mindustry Block.researchRequirements 公式：round10(60*mult + buildAmount^1.11 * 20 * mult * perItem) 喵
    double raw = 60 * mult + Math.pow(buildAmount, 1.11) * 20 * mult * perItemMult;
    return (int) Math.round(raw / 10.0) * 10;
}
```
- v1：`effectiveRequirements` 直接用显式 `requirements`，公式不参与，最可控喵。
- v2：若节点给 `buildCost`，则每项 `count = researchCost(costMultiplier, buildCost.get(item), perItemMultiplier.get(item,1f))`，倍率由 `ResearchTree` 从父链累乘后传入喵。
- 倍率累计：`ResearchTree` 初始化时从根 DFS，`child.effMult = parent.effMult * child.costMultiplier`，perItem 同理累乘，镜像 Mindustry `TechNode` 构造逻辑喵。

## 二、存档喵

### 2.1 机制对比与选择喵
| 方式 | 优点 | 缺点 | 结论喵 |
|---|---|---|---|
| `SavedData` 挂 `server.overworld()` | 显式 setDirty、vanilla 标准、按世界文件落盘 | 无自动同步，需自写 payload（本来就要写） | **推荐**，class 名沿用 T14 建议的 ResearchData 喵 |
| Level attachment（现有 mod 风格） | 与 TEAM_STORAGE/BLOCK_TEAM 一致 | `getData` 原地改不标记 dirty，必须 `setData` 才持久化（现有队伍存储疑似有潜在未持久化坑） | 备选，若团队坚持 attachment 则照抄 serializer 模式，但每处变更必须 setData 喵 |

**结论**：用 `ResearchSavedData extends SavedData` 存**每世界一份、跨维度共享**（读/写统一走 `server.overworld()`），对应 Mindustry 单存档全局研究，且新世界自动清零喵。

### 2.2 ResearchSavedData 结构与 NBT 喵
`com.blockdustry.research.ResearchSavedData` 喵：
```java
public class ResearchSavedData extends SavedData {
    private final Set<ResourceLocation> unlocked = new HashSet<>();          // 已解锁节点 id 喵
    private final Map<ResourceLocation, Map<ResourceLocation, Integer>> progress = new HashMap<>(); // 节点id -> (物品id -> 已投入) 喵
    public static final String DATA_NAME = "blockdustry_research";            // 落盘键名喵

    public static ResearchSavedData get(ServerLevel level) {
        DimensionDataStorage storage = level.getServer().overworld().getDataStorage();
        return storage.computeIfAbsent(
            new SavedData.Factory<>(ResearchSavedData::load, ResearchSavedData::new), DATA_NAME);
    }
    // unlocked: CompoundTag 数组 or ListTag of String 喵
    // progress: CompoundTag{ nodeId: CompoundTag{ itemId: int } } 喵
    // 全用 RL 字符串 + int，load 不需 HolderLookup，最简单喵
    public static ResearchSavedData load(CompoundTag tag) { ... }   // 直接读字符串，无 RegistryLookup 依赖喵
    @Override public CompoundTag save(CompoundTag tag, HolderLookup.Provider p) { ... }  // 写回，返回非空喵
    // 每处变更（unlock/progress）末尾显式 setDirty() 喵
}
```
存取语义喵：
- `isUnlocked(RL)` / `unlock(RL)`（setDirty）喵。
- `getProgress(nodeId, item)` / `addProgress(nodeId, item, n)`（setDirty）喵。
- `isFullyResearched(RL)`：progress 覆盖该节点有效需求全部喵。
- 与团队存储的隔离：研究是**世界级**，不按玩家/队伍分（Mindustry 多人同队共享研究；MC 简化为一服一树）喵。

### 2.3 多人同步喵
沿用现有 payload 模式（`CustomPacketPayload` + `StreamCodec` + `@EventBusSubscriber(modid, bus=MOD)` 注册，可独立新类，不碰共享 `BlockdustryNetwork.java`）喵：
- `ResearchStatePayload`（S→C，全量）：`Set<String> unlocked` + `Map<String, Map<String,Integer>> progress`，供屏幕/创意栏过滤用喵。
- `ResearchUnlockPayload`（S→C，增量）：`String nodeId`，用于解锁音效/飘字喵。
- `ResearchSpendPayload`（C→S）：`String nodeId`，客户端点节点发「尽量研究」请求喵。
- `QueryResearchPayload`（C→S，可选兜底）：开屏时刷新一次，防 join 同步时序问题喵。

同步时机喵：
- `PlayerEvent.PlayerLoggedInEvent`（服务端，`ResearchManager` 订阅）→ `sendToPlayer(new ResearchStatePayload(...))` 全量喵。
- 每次 unlock / progress 变更 → `PacketDistributor.sendToAllPlayers` 全量（v1 节点少，全量最简单；量大再改增量）喵。
- 服务端权威：客户端状态只读展示，所有修改经 `ResearchSpendPayload` 到服务端校验再写喵。

### 3.2 ResearchGateHandler（新文件，服务端权威）喵
`com.blockdustry.research.ResearchGateHandler`，`@EventBusSubscriber(modid = Blockdustry.MODID)` 自动注册喵：
```java
@SubscribeEvent
public static void onPlace(BlockEvent.EntityPlaceEvent event) {
    if (event.getLevel().isClientSide()) return;                       // 只服务端兜底喵
    if (!(event.getPlacedBlock().getBlock() instanceof BlockdustryBuildingBlock)) return; // 只拦本 mod 建筑喵
    if (!(event.getEntity() instanceof ServerPlayer player)) return;   // 非玩家放置（命令/活塞）不拦喵
    if (player.getAbilities().instabuild) return;                      // 创造模式默认绕过（与 Mindustry sandbox 全解锁一致，可加 config 开关）喵
    ResearchNode node = ResearchTree.nodeForBlock(event.getPlacedBlock().getBlock());
    if (node != null && !node.defaultUnlocked()
            && !ResearchManager.isUnlocked((ServerLevel) event.getLevel(), node.id())) {
        event.setCanceled(true);                                       // 取消放置喵
        player.sendSystemMessage(Component.translatable("blockdustry.research.locked",
                getBlockName(node)));                                   // 提示需要研究喵
    }
}
```
要点喵：
- 与现有 `BlockdustryTeamHandler`（同事件）共存，`@EventBusSubscriber` 各自订阅不冲突喵。
- `defaultUnlocked` 节点直接放行，根节点 core 等无需进树喵。
- 门控 map `block->node` 由 `ResearchTree` 构建（unlockContent 解析为 Block 后建索引）喵。
- 若担心恶意客户端绕过 anchor 直接放 fill 格：fill 格同 block，也会被本 handler 拦（`getPlacedBlock` 同 block id）喵。

### 3.3 服务端兜底 vs 客户端显示喵
- 服务端 `EntityPlaceEvent` 是**唯一权威**，客户端过滤只是 UX，绝不能只做客户端喵。
- 客户端显示：`ResearchClientCache` 缓存已解锁集合；创意栏/提示/Jade 都读它喵。
- `ResearchManager.isUnlocked(ServerLevel, RL)` 与 `isUnlockedClient(RL)` 分开，服务端永远查 SavedData，客户端永远查缓存喵。

## 四、UI喵

### 4.1 ResearchScreen 设计喵
`com.blockdustry.client.ResearchScreen extends Screen` 喵：
- **v1 竖排缩进树**（父左子右、按 depth 缩进，类似资源管理器），比 Mindustry 左右均衡拼树简单得多且可读喵。
- 每个节点一个按钮（`Button` 或自绘 `AbstractWidget`）喵：
  - 图标：`guiGraphics.renderItem` 画解锁内容物品/方块图标喵。
  - 名称：`block.blockdustry.xx` 本地化喵。
  - 状态：已解锁=绿框普通；可研究（父全解锁+未解锁+进度未满）= 可点，显示需求与每项 `已投入/需求` 进度条；不可研究=灰/红+锁（用 `fill` 画锁形或叠加 `Icon`）喵。
  - 进度条：`guiGraphics.fill` 画背景+前景，比例 = 该节点已投入物品数 / 总需求数（Mindustry 按价值加权，v1 简化为计数占比，上限 99%）喵。
- 点击节点 → 若可研究则 `PacketDistributor.sendToServer(new ResearchSpendPayload(nodeId))`；服务端回 `ResearchStatePayload` 后 `init()` 重建刷新喵。
- **v2 连线树**：父-子连线用 `fill` 画 2px 横/竖线段（`GuiGraphics` 无原生 line，用细矩形代替；本 mod 已有 Tesselator 画激光的先例，但 fill 最稳），父解锁亮色/否则灰喵。
- `shouldPause()` 返回 true（Mindustry 研究面板暂停游戏）喵。
- 滚动：节点多时用 `ScrollPanel` 或简单 `guiGraphics.enableScissor` + 上下按钮，v1 节点少可先不滚喵。

### 4.2 打开方式喵
`com.blockdustry.client.ResearchScreenHandler`（`@EventBusSubscriber(modid, bus=MOD, value=CLIENT)` 自注册按键）喵：
```java
public static final KeyMapping KEY_RESEARCH = new KeyMapping(
        "key.blockdustry.research", InputConstants.Type.KEYSYM, InputConstants.KEY_J, "key.categories.blockdustry");
@SubscribeEvent static void regKey(RegisterKeyMappingsEvent e) { e.register(KEY_RESEARCH); } // MOD bus 喵
@SubscribeEvent static void onTick(ClientTickEvent.Post e) {                                 // FORGE bus（同 class 可双 bus 各一？→ 拆两个 class 或都用 FORGE）喵
    while (KEY_RESEARCH.consumeClick()) {
        if (mc.screen == null) mc.setScreen(new ResearchScreen());
    }
}
```
注意：一个 `@EventBusSubscriber` 类只能挂一个 bus，故拆两个类或把按键注册放到现有 `BlockdustryClient`（共享文件，主会话整合）。推荐拆 `ResearchKeyRegistrar`（MOD bus 注册键）+ `ResearchScreenHandler`（FORGE bus 检测按下）两个文件，避免改共享文件喵。另外可在 `CoreHudHandler` 加个「科技树」小按钮（共享文件，留 v2 由主会话加）喵。

### 4.3 材料从哪扣喵
- **v1 玩家背包**（推荐起步）喵：
```java
// ResearchManager.spend 内，对每项需求取缺口 need，背包尽力扣喵
int removed = player.getInventory().clearOrCountMatchingItems(s -> s.is(item), need, player.getInventory());
```
- **v2 队伍核心共享池**（忠于 Mindustry `ResearchDialog.spend`）喵：`BlockdustryTeamStorage.get(level, team)` 逐个 `take(item)`；**必须**在扣完后 `level.setData(BlockdustryAttachments.TEAM_STORAGE.get(), map)` 触发持久化（现有 Storage.take/add 不标记 dirty，直接改不落盘）喵。扣取顺序建议「共享池优先、背包兜底」，对应 Mindustry「核心库存优先、当前核心最后」喵。
- 服务端统一在 `ResearchManager.spend(ServerPlayer, RL, int)` 处理：校验 `canResearch`（父全解锁、未解锁）、扣材料、记 progress、满则 `unlock` 递归、setDirty + 广播喵。

## 五、成本与默认解锁喵

### 5.1 默认解锁节点表喵
当前 mod 方块（`BlockdustryBlocks`）建议默认解锁（`defaultUnlocked=true`，需求空，对应 Mindustry 免费自动解锁节点）喵：
| 默认解锁 | 理由喵 |
|---|---|
| core（核心） | 根节点，玩家出生即需要喵 |
| conveyor / router（传送带/路由器） | 基础物流，开局必备喵 |
| drill（机械钻头） | 基础采集喵 |
| power_node / combustion_generator（电力节点/燃烧发电机） | 基础电力起步喵 |
| graphite / lead / silicon（材料物品） | 物品不参与门控（v1），直接可用喵 |

需研究（示例，可再调）喵：
| 需研究节点 | 建议需求（v1 显式）喵 |
|---|---|
| graphite_press（石墨压缩机） | 煤 40 喵 |
| battery（电池） | 铅 30 喵 |
| turret（双管） | 煤 20 + 铅 30 喵 |
| scatter（分裂） | 煤 30 + 铅 50 喵 |
| unit_factory（地面单位工厂） | 硅 40 + 铅 40 喵 |
| fuse / arc（熔毁/电弧） | 煤 50 + 硅 60 喵 |
| elevator（垂直提升机） | 煤 30 喵 |
| power_source / item_source（调试源） | 默认解锁（沙盒调试）喵 |

### 5.2 researchCostMultiplier 融入喵
- v1：倍率不参与，`requirements` 显式写死，最简单可控喵。
- v2：`ResearchTree.effectiveRequirements` 沿父链累乘 `costMultiplier` 与 `perItemMultiplier`，每项按 `ResearchCost.researchCost(mult, buildAmount, perItem)` 算出；根可设全局倍率（如 Erekir 全物品 0.9），后代几何增长，镜像 Mindustry 喵。
- 提供 `/blockdustry research unlock <id>`、`/blockdustry research reset` 调试命令（复用 `RegisterCommandsEvent`，见 `BlockdustryCommands` 模式）喵。

## 六、类/文件清单与实现顺序喵

### 6.1 类/文件清单（全部新文件，不碰共享注册文件）喵

### 6.2 实现顺序与并行拆分喵
主会话定接口后（ResearchNode 字段 + ResearchManager 公开 API 见 6.3），三组可并行喵：
- **组 A（数据/存档/门控，可并行）**喵：
  - Agent A1：`ResearchNode` + `ResearchNodes` + `ResearchTree` + `ResearchCost`（先出，其余依赖其 id 规范）喵。
  - Agent A2：`ResearchSavedData` + `ResearchManager`（isUnlocked/spend 骨架，等 A1 的 ResearchTree 接口）喵。
  - Agent A3：`ResearchGateHandler`（等 ResearchManager.isUnlocked）喵。
  - 依赖：A2/A3 依赖 A1 的公开接口，接口先冻结则同批并行喵。
- **组 B（网络/UI，A 完成后并行）**喵：
  - Agent B1：`ResearchNetwork` + 4 个 Payload + `ResearchClientCache`（依赖 ResearchSavedData 结构与 ResearchManager.spend）喵。
  - Agent B2：`ResearchScreen` + `ResearchKeyRegistrar` + `ResearchScreenHandler`（依赖 B1 的 payload 与 ResearchClientCache）喵。
- **组 C（整合，主会话）**喵：合并 lang、编译、`Blockdustry.java` 加一行启动日志（可选）、runClient 实测喵。

### 6.3 关键接口（供并行 agent 对齐）喵
```java
// ResearchTree 喵
public static ResearchTree get();                                   // 惰性单例喵
public ResearchNode node(ResourceLocation id);                      // 按 id 查喵
public ResearchNode nodeForBlock(Block block);                      // 门控：block->node 喵
public boolean hasNode(ResourceLocation id);                        // 存在性喵
public Map<ResourceLocation, Integer> effectiveRequirements(ResearchNode node); // 含倍率累乘喵
public boolean isRoot(ResearchNode node);                           // 无父喵
public List<ResourceLocation> childrenOf(ResourceLocation id);      // 画树/自动解锁用喵
// ResearchManager 喵
public static boolean isUnlocked(ServerLevel level, ResourceLocation id);      // 服务端查 SavedData 喵
public static boolean isUnlockedClient(ResourceLocation id);                   // 客户端查缓存喵
public static boolean canResearch(ServerLevel level, ResourceLocation id);     // 父全解锁 + 未解锁喵
public static int spend(ServerPlayer player, ResourceLocation id, int amount); // 扣料/记进度/满则解锁，返回扣了多少喵
public static void syncToPlayer(ServerPlayer player);                          // join/变更推送喵
```
自动解锁：`spend` 中节点满 → `unlock(id)` → 递归 `unlock(parent链)` + 扫 children 中「父全解锁 + 有效需求空 + defaultUnlocked 或免费」的节点自动解锁（镜像 Mindustry `checkAutoUnlocks`）喵。

## 七、风险与待人工排查喵
1. **Level attachment dirty 坑**：现有 `BlockdustryTeams.setTeam`/`BlockdustryTeamStorage` 原地改 `getData` 返回的 map 未 `setData`，疑似不落盘；研究层用 SavedData（显式 setDirty）规避，但「队伍共享池扣料」v2 必须补 `setData` 喵。
2. **跨维度**：研究统一走 `server.overworld()`，其他维度访问时别直接用 `level.getDataStorage()` 喵。
3. **EntityPlaceEvent 取消行为**：NeoForge 1.21.1 取消该事件会回滚 BlockSnapshot（应能拦住），但需实现时实测「客户端幽灵预览」与「物品是否不消耗」喵。
4. **创造模式**：默认绕过门控，是否加 config 开关由主会话定喵。
5. **一服一树**：多人所有玩家/队伍共享研究进度；若以后要「按队伍分树」，需把 unlocked 改成 `Map<Team, Set<RL>>`，接口预留但不实现喵。
6. **数据包 registry（v2）**：客户端进服前必须有树数据，DataPackRegistry 随连接同步可满足，但要确认 Screen 打开时数据已到位（有 QueryResearchPayload 兜底）喵。
