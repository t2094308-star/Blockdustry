# T9 三维物流 阶段产出喵

## 目标喵
参考《戴森球计划》(DSP) 学习三维物流设计思路，结合现有 Blockdustry 平面物流（传送带/Router/物品源），提出上下坡传送带、垂直提升机、立交桥等三维物流可行方案，并给出优先级与分阶段实现建议喵。本任务只读+写文档，不改游戏源码喵。

---

## 一、DSP 三维物流思路提炼（仅学习设计思想，不抄代码）喵

### 1.1 DSP 物流五件套（反查 `DSPGAME_Data/Managed/Assembly-CSharp.dll` 元数据）喵

| 组件 | 类/机制 | 职责 |
| --- | --- | --- |
| 传送带 | `BeltComponent` + `CargoPath` | 平面逐段运货 |
| 分拣器 | Sorter（旋转臂，短距） | 带↔建筑、带↔带跨层转物 |
| 分流器/堆叠机 | `SplitterComponent` / `PilerComponent` | 分流（优先级/交替输出）、堆叠 |
| 物流站 | `StationComponent` + `DroneData`/`DroneComponent` | 供需配对，无人机 3D 直飞 |
| 运输船 | `LogisticShip` | 星际远距网络 |

### 1.2 关键发现：DSP 的「三维」不是斜坡，而是「网络层绕行平面带网」喵

- 传送带本体是**平面**的，`CargoPath` 里没有真 y 高度字段，不存在原生上下坡带喵。
- 垂直移动靠两个机制：**分拣器**（短距跨层转移臂）与**物流塔+无人机**（网络直飞）喵。
- 玩家社区的「螺旋传送带」是用分拣器阵列手工拼出的视觉上坡，不是原生方块喵。
- 启示：DSP 的 3D 是「用一个网络层绕过平面带网」；而 MC 有真实 y 轴，上下坡/高架是 MC 的原生优势，比 DSP 更直接喵。

### 1.3 CargoPath 建模（链路式连续缓冲）——不采纳实现，借鉴思想喵

- 一整条带线 = 1 个 `CargoPath`：`buffer`（环形 itemId 缓冲）+ `chunks`（分段）+ `pointPos/pointRot`（几何点）喵。
- `head` = 输出端，`rear` = 输入端；物品在统一 buffer 里整体推进，`TryInsertItemAtHead`/`TryPickItemAtRear` 从两端进出喵。
- 断带/接带/开口 → `PathSplit/PathConcat/PathOpen/PathTrunc` 重排 buffer；`AddRelatedBelt/AddRelatedInputPath/SetOutput` 维护拓扑喵。
- 与 Mindustry/Blockdustry「每格 3 槽、逐格推进」模型不同：全链路合并模型吞吐高，但插入/断开要重排整个 buffer，对 MC 逐格 BE tick 性价比低，**不采纳**喵。但「头尾方向语义 + 带路可被建筑打断/合并」的建模思想值得保留（如拆带处物品不应凭空消失）喵。

### 1.4 CargoTraffic 集中式组件池——与现有方向一致喵

- `beltPool/pathPool/splitterPool/monitorPool/spraycoaterPool/pilerPool` + cursor/capacity/recycle 的**对象池**集中管理所有物流组件喵。
- 启示：Blockdustry 已有 `BlockdustryBuildings` 全局注册表 + `BlockdustryTicks` 统一模组 tick，方向一致；对象池对 MC BE 生命周期模型非必需，但「统一注册中心 + 分组件池」的扩展思路可参考喵。

### 1.5 物流塔 = 供需配对网络（DSP「塔/垂直绕行」的答案）喵

- `StationComponent`：`HasLocalSupply/HasLocalDemand`、`AddLocalPair/AddRemotePair`、`DispatchSupplyShip/DispatchDemandShip`、`CalcLocalSingleTripTime/CalcTripEnergyCost`、`InternalTickLocal/Remote` 喵。
- `DroneComponent`：`targetObjectId/targetPos/movement/progress` 直飞动画；`DroneData` 带 `itemId/itemCount/stage` 喵。
- 启示：物流塔 = 收集物品 + 注册供给/需求 + 无人机直飞送达，绕过平面带网喵。
- Blockdustry 已有 `PowerGrid/PowerGridManager`（每 tick Union-Find 重建连通）可作拓扑骨架；但物流网是**需求驱动的定向派发**（supply/demand 配对 + 距离/能量费用），比无向电网复杂，不能直接照搬喵。

## 二、结合 MC 三维与现有 Blockdustry 的可行方案喵

### 2.1 现有接口衔接点（改动最小原则）喵

- `ConveyorBlockEntity.directionOf(source)` 目前只遍历 `Direction.Plane.HORIZONTAL` → 需扩展接受 UP/DOWN 邻接（来源在 `.above()/.below()`）喵。
- `ConveyorBlockEntity.tickAnchor` 出口 `front = pos.relative(facing)` → 坡道改 `.relative(facing).above()/.below()`，垂直提升机改 `.above()` 喵。
- `BlockdustryBuildingEntity.dumpItem` 只扫水平四邻 → 垂直物流需把 `UP/DOWN` 加进候选扫描（或提供 dumpItem 变体）喵。
- `BlockdustryItemSource/Sink`（`getTeam()/getPos()` + `acceptItem/handleItem`）接口**无需改签名**，方向判定在各 BE 内部完成喵。
- `BlockdustryBlocks` 需为新方块补 block + BlockItem + BE type + 创造栏 tab 注册；blockstate variant 膨胀用仓库 python 脚本生成（现有 80 variant 惯例）喵。

### 2.2 方案 A：上下坡传送带（推荐先做，详见 `docs/传送带上下坡.md`）喵

- `ConveyorBlock` 加 `SLOPE` 枚举（FLAT/UP/DOWN），物品 y 随 `progress` 用 smoothstep 从 0→1 格抬升，出口/尾插坐标按坡度切到 `.above()/.below()` 喵。
- 完全复用现有 3 槽进度系统 + NBT，只改块状态与交接坐标喵。
- 工作量：小（约 1-2 天）喵。

### 2.3 方案 B：垂直提升机（DSP 塔的本地化替代 + Mindustry Duct 风）喵

- B1（推荐先做）：Duct 式单格垂直带，一格存 1 件 + `progress∈[0,1]`，`front=pos.above()`，一列 n 格就是 n 段接力，任意高度、零新概念喵。
- B2（二期）：anchor BE 管理整列，`vProgress` 贯穿全高，吞吐高，但需列长/跨格 NBT，复杂度高喵。
- 工作量：B1 小（约 1-2 天），B2 中（约 2-3 天）喵。

### 2.4 方案 C：立交桥 / 高架交叉不干扰（MC 原生优势）喵

- MC 天然 3D：现有带占格内 y 0-4，把另一条带铺到 y+1 的空块即可交叉；两个 BE 互相独立，`directionOf` 只查水平不会误连，**天然不干扰**喵。
- 需要补「高架传送带」放置语义：可先直接允许放任意面（最省），或要求底部有支撑块（Create 风，更精致）喵。
- 与方案 A 组合：上坡 → 高架平带 → 下坡 = 完整立交喵。
- 工作量：仅支撑逻辑约 1 天；若只靠放高空甚至无需新方块喵。

### 2.5 方案 D：分拣器（DSP Sorter 风，短距跨层转移臂）喵

- 小方块 + 旋转臂：物品在「拾取点→投放点」两点间摆动传递，两点可在不同 y（如地面带 → 高一格建筑输入）喵。
- 独立新方块 + 新 BE + 动画，不依赖现有带槽，天然支持跨层喵。
- 工作量：中高（约 3-5 天）喵。

### 2.6 方案 E：物流塔 + 无人机网络（DSP 塔，远期「垂直绕行」）喵

- 塔收集物品、注册供给/需求，无人机直飞送达（粒子/实体动画，物品瞬移式移交，忠实 Mindustry 简化、避免真物理）喵。
- 复用 `PowerGridManager` 的 Union-Find 拓扑骨架；新增供需配对 + 派发逻辑喵。
- 工作量：高（约 1-2 周），需 UI 配置 supply/demand/数量喵。

## 三、优先级与分阶段建议喵

| 阶段 | 内容 | 工作量 | 优先级 | 依赖 |
| --- | --- | --- | --- | --- |
| P1 | 方案 A 上下坡传送带 | 小 | 高 | 无 |
| P1 | 方案 B1 垂直提升机 | 小 | 高 | 无 |
| P2 | 方案 C 立交桥（高架/支撑） | 小 | 中 | A 或独立 |
| P2 | 方案 D 分拣器 | 中高 | 中 | 无 |
| P3 | 方案 E 物流塔网络 | 高 | 低（远期） | PowerGrid 骨架 |

推荐路线喵：
1. 先做 P1 的 A + B1：完全复用现有带槽与 progress 语义，改动面最小，2-3 天可见「上下坡 + 直上直下」效果喵。
2. 再做 P2 的 C：顺势补高架与立交，成本低、演示性强喵。
3. D（分拣器）作为趣味元件按需插入喵。
4. E（物流塔网络）等物流规模起来后再上，复用电力网络骨架即可喵。
